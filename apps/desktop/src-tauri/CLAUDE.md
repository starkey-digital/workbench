# Desktop-only Rust (`src/`)

Crate `workbench` (lib `workbench_lib`). Pure logic belongs in `crates/workbench-core`; commands here are thin shells.

- `main.rs` / `lib.rs` — entry, plugin registration, `build_invoke_handler!` macro, state management
- `commands.rs`, `git_commands.rs`, `trello_commands.rs` — thin `#[tauri::command]` shells calling `workbench_core`
- `autostart.rs` — Start on startup over the `auto-launch` crate (no `tauri-plugin-autostart`; macOS LaunchAgent, Windows HKCU Run key; commands `autostart_enabled`/`set_autostart`). Login launches pass `--autostart` and start minimised; dev builds use a separate "Workbench Dev" entry. On startup (release only) an enabled entry is repaired: it gains the flag and follows the app if its target is gone, but a Task Manager disable is never undone. Settings: `components/settings/autostart.svelte.ts` (the OS item is the source of truth), platform checks from `utils/platform.ts` (`IS_WINDOWS`/`IS_MAC`).
- `hook_bridge.rs` (subscribes to the server's bridge (`ServerControl::hooks`): logs Claude hooks, requests project refreshes from them, keyed on the hook cwd's repo root, and re-emits Codex `notify` as `codex:notify` for labels), `git_watcher.rs`, `github_poller.rs`, `refresh_dispatcher.rs`, `menu.rs` (native app menu, macOS only: Win32/GTK menu bars ignore the dark theme; elsewhere Ctrl+, opens Settings; the ActivityRail's update button above Settings checks for updates on every platform), `native_terminal*` (macOS)
- `server_control.rs` — `ServerControl` owns ONE `workbench_server::Managers` (terminals + chats) shared by two listeners: the always-on **loopback** listener (desktop xterm panes; per-process in-memory token from `workbench_core::token::generate`, handed to the webview only via `terminal_server_status`, never persisted or put in a shell env) and the opt-in **LAN** listener (`start_server`/`stop_server`/`server_status`; `rotate_server_token`). Terminals therefore show on the phone and vice versa, and survive LAN restarts. The LAN slot remembers its token: `start_server` with a different token restarts it, and `rotate_server_token` is the one rotation path (loads settings from disk, replaces only `serverToken`, saves, restarts a running listener on its bind/port, emits `settings:changed`) so unsaved form edits never ride along. Both listeners also get the `HostControl` (`host_update.rs` `DesktopHost`) behind `/host/update`: download, `kill_all_sessions`, install, restart. It is the only updater, with one contract: the desktop's `UpdaterStore` is UI state over the `host_update_status` (`fresh`) / `host_update_install` (`version`) commands, the same names, args and `workbench_server::host::Install` wording as the phone's `GET /host/update?fresh=` / `POST {version}`. An install names the version the client reviewed and is refused (409) when the feed now offers another; without one (older phones) it takes what is available. `UpdateGuard` allows one install at a time and records its `UpdateOrigin` (`desktop`|`remote`); a second request joins the running one, and a check while installing reports its version and `startedBy`. Every install emits `update:installing` (`{version, origin}`), `update:progress` (`{downloaded, total}`, ≤ every 100ms plus a final one) and `update:failed` (`{error, origin}`). There is no JS `plugin-updater` and no `plugin-process` at all (Rust restarts with `app.restart()`).
