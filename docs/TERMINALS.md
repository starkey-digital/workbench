# Terminals

Terminal IO and how clients render the server-owned workspace. CLAUDE.md keeps a summary of each section.

## PTY IO

**PTY IO never blocks a shared thread.** A PTY master write blocks once the shell's input queue (~1 KB on macOS) is full, e.g. a paste while a foreground job isn't reading. So each terminal writes on its own thread: server terminals (`terminal.rs` `spawn_writer`) take input from a bounded queue (`INPUT_QUEUE`), and the attach loop holds a chunk the queue can't take and stops reading that socket until there's room (output, takeover and revoke still flow; held input is dropped after a takeover); `type_keys` and the startup command queue too. Native terminals (`native_terminal.rs`) queue keystrokes from SwiftTerm's main-thread `input_callback` and `write_native_terminal` on an unbounded queue (no producer may block), never call `swift_term_resize` (a `DispatchQueue.main.sync`) while holding the session lock, and hand output to SwiftTerm and `terminal:data` at most once per 33 ms frame (`pump_output`; a UTF-8 character cut at a frame's end waits for the next). Create/resize/kill run on `crate::blocking`; resizes record the requested frame first and each applies the latest, so pool reordering can't leave a stale size. `swift_term_destroy` is synchronous, so `destroy_view` (kill and shell exit) frees the callback context only once no callback can run. A terminal client that falls behind its output (`RecvError::Lagged`: the socket and the native view alike) gets clear-screen plus the scrollback on a fresh subscription taken under the buffer lock (`TerminalSession::resync`), so nothing is replayed twice; a replay of a full ring starts at its first line. On Unix only `terminate_process_group` reaps a shell, after signalling its group; `list()` peeks with `waitid(WNOWAIT)`, and a shell reaped once is never signalled again (its pid may be reused). Every server WS send (terminal and chat) goes through `state::ws_send`/`ws_close`: 30s plus 1s per 16 KB of frame, then the socket is dropped, so a phone that stopped reading can't pin its task or hold up a revoke/takeover. `apps/server/tests/terminal_input.rs` pastes 512 KB into a sleeping shell on a one-worker server runtime and checks `/health` and the bytes.

## Workspace rendering

**Workspaces are the server's.** The workspace → tab → pane model lives in the embedded server (`WorkspaceService`, `docs/WORKSPACE_MODEL.md`); the desktop is one of its renderers, the phone another. `WorkspaceStore` (`stores/workspaces.svelte.ts`) holds the latest snapshot from `transport().subscribeWorkspace` (`GET /events/workspace` on the loopback listener; `WorkspaceStream` in `@workbench/transport` reconnects with backoff and drops frames whose `rev` isn't newer, a new connection's first frame excepted) and maps it to the view types (`ProjectWorkspace`/`TerminalTabState`/`TerminalPaneState`, with each pane's runtime: `terminalId`, `status`, `title`, `busy`, `waiting`). Every change is one `workspaceCommand` (30s budget; a `newSession` carries a `requestId` and is resent once on no answer, applied once by the server's last-256/5-min cache) (open/close workspace, closeProject, newSession incl. resume/prompt/account, closePane/closeTab, restart, setCodexMode, rename, split, move, trustFolder) and shows in a later snapshot; a refusal is a toast. What a command opened is selected at once and kept from pruning until a snapshot shows it (10s at most: a command whose publish wait timed out answers with an older `rev`). While the stream is down (`status(false)`), `WorkspaceStore.streamLive` is false and `PersistenceBanner` shows "Reconnecting". Per-device state (`stores/workspace-ui.ts`: selected workspace, active tab per workspace, Claude panes shown as chat) is in localStorage keyed by server ids, pruned when ids leave the snapshot, every access in try/catch. Nothing here creates a process: `TerminalPane` attaches to `pane.terminalId` (keyed on it, so a restart's new terminal is followed), a native pane shows the same server terminal in SwiftTerm (`attach_native_terminal`/`detach_native_terminal`; a detached view leaves the terminal running), `SessionChat` attaches by `sessionId` (its Restart is the pane's `restart` command via `AgentChat.onRestart`, and it re-attaches when the pane runs again), and `PaneState` covers starting / needs-trust / exited (Restart for AI panes, Close for shells). A pane that leaves the snapshot, or leaves `chatPanes`, releases its chat. `TerminalPane`/`NativeTerminalPane` check a `destroyed` flag after every `await` in their async `onMount`, so a pane re-keyed mid-setup leaks no socket, WebGL context or SwiftTerm view. A session opened on any device is a tab here, and an End anywhere removes it everywhere. The server allows ONE terminal attacher: a new attach sends `{"t":"takeover"}` and the old pane shows "Take control" (never auto-reattach, or two devices ping-pong). A socket that drops with no `exit`/`takeover`/`revoked` frame (sleep, missed heartbeat) is `dropped`: "Connection lost" + Reconnect, also never automatic, since its takeover frame may be what was lost. The desktop no longer reads or writes `workspaces.json`; its git watcher follows the snapshot's projects (`watch_git_projects`). A snapshot's `persistence` other than `ok` (unreadable file kept aside, or another process holds the lock) shows `PersistenceBanner`; its `local` (an older desktop's saved selection, tabs and chat views) seeds `WorkspaceUi` once when this device has none. A chat re-attaches when its pane's `generation` changes (`chat-registry` `followPane`, also called from `WorkspaceStore.apply` for each pane whose status or generation changed, so a hidden chat follows a restart too). Native views are keyed by terminal id, so a restart's attach and the old view's detach never collide. Editing a project's path or name sends `updateProject` (`ProjectStore.update`).
