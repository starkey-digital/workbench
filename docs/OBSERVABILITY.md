# Observability

Sentry and logging details. CLAUDE.md keeps a summary of each section.

## Frontend

**Frontend:** `@sentry/svelte`, set up by `@workbench/telemetry` (`packages/telemetry`, the one place both webviews' Sentry code lives: `initSentry`, `captureChatDiagnostic`, `captureViewError`, `breadcrumb`/`chatBreadcrumb`, the shared DSN). Each app's `sentry.ts` is a thin `initSentry()` passing its release and whether to report; `src/main.ts` calls it before mount for **both** the main and settings windows. Prod-gated: `enabled` is `import.meta.env.PROD && MODE !== 'test'`. DSN is a public write-only key in the package, overridable via `VITE_SENTRY_DSN` (empty disables). Sentry's `Console` integration is off in both apps: console lines carry error text with paths (desktop keeps them in `workbench.log`). Release tag `workbench@${__APP_VERSION__}` (`__APP_VERSION__` from `vite.config.ts` ← `tauri.conf.json` version). chat-ui never imports Sentry: hosts pass `report` (drift, bad frames; `throttled`) and `breadcrumb` (the chat trace's events but streamed updates) to `AgentChat`. `ViewBoundary` (`@workbench/ui/view-boundary`, a `<svelte:boundary>`) walls off the chat body (desktop `SessionChat`, mobile `ChatScreen`, with the chat trace and Resync on Reload) and terminal panes (desktop `TerminalGrid`, mobile `PaneScreen`, the one back handler for its chat and terminal so a failed view can still be left): a render error is reported with its `view` tag and replaced by "Reload view".

## Backend logging

**Backend logging:** `observability::init` also installs a global `log` logger (`env_logger` → stderr and `<config dir>/logs/workbench.log`, rotated once past 5 MB at startup; respects `RUST_LOG`, default `info`) wrapped by Sentry. The server's `tracing` events reach it through tracing's `log` feature, including `watchdog.rs`'s: an error when the server runtime's async workers or blocking pool leave a task waiting 1s (macOS also writes every thread's stack to `logs/stall-<unix secs>.txt` with `/usr/bin/sample`, at most every 10 min, newest 10 kept), when the watchdog itself runs 5s late (the whole process stopped, e.g. swapped out under memory pressure; preceded by a breadcrumb with swap use and the machine's swap-ins during the freeze (`vm.compressor.swapper.swapins_total`, system-wide; not the kernel pressure level, which stayed `normal` through freezes with swap nearly full); skipped on Windows, whose clock may count the machine's sleep; on macOS also when `kern.sleeptime`/`kern.waketime` changed meanwhile (the monotonic clock runs through DarkWake) or a thread sample ran (`sample` suspends the process), both a breadcrumb only; a probe whose spawn itself blocks is its own report, never a freeze), or when open files pass 80% of the limit (each kind of stall or freeze is an error at most every 10 min, a warning otherwise), and a warning per request unanswered after 45s. The desktop's `run()` and the standalone `main` raise the soft open-file limit at start (`watchdog::raise_fd_limit`; spawned shells inherit it, see its doc): launchd gives a GUI app 256, and at that ceiling `accept` fails and the API stops answering (`apps/server/tests/fd_limit.rs`). The desktop `Info.plist` sets `LSAppNapIsDisabled`: App Nap is the suspected cause of whole-process freezes of up to a minute with no swap-ins (WORKBENCH-K), and it would also stop the servers the phone talks to. Whoever builds the server's runtime calls `watchdog::start`. The server runs its own accept loop (`accept.rs`) so each accepted socket gets TCP keepalive, a 30s limit on sending a request's headers, and a 60s limit on a write that makes no progress (`WriteDeadline`: a peer that stops reading but still ACKs, which keepalive never catches, would hold an SSE stream or long poll forever), and terminal/chat WebSockets are pinged every 30s and dropped after two missed pongs (`state::Heartbeat`; `WORKBENCH_WS_PING_MS` for tests), so a vanished phone's sockets are freed (`tests/dead_peer.rs`). In release: `log::error!` → Sentry **event**, `log::warn!`/`log::info!` → **breadcrumb** (shown on the next event). The chat path logs at `info` with a short session id and never text, titles or tokens: busy/idle changes and the line or request that made them (`session.rs` `note_busy`), WS attach and close (reason), resyncs and lag, plugin hellos, stale-link drops and line gaps; `warn` for refused input (a full `/mod/in` queue) and a replaced worker's lines. Use `log::warn!`/`log::error!` for backend diagnostics, **not** `eprintln!`. Stderr output works in all builds; Sentry forwarding only in release.

## Details

- **Extended diagnostics (opt-in, `extendedDiagnostics`, default off; Settings → General → Privacy):** errors-only reporting is the same either way. On, error reports also carry breadcrumbs for chat sockets (`chat.ws`: connect, snapshot, resync, close code, retry, gave-up…) and terminal sockets (`terminal.ws`: open, takeover/exit/revoked, dropped/refused/closed with close code; desktop and phone), and the 200-entry chat trace as `chat-trace.json` on drift, bad-frame and view-error reports. Counts, flags, close codes and fixed labels only: never prompts, replies, titles, paths, URLs or tokens. Applied live (`setExtendedDiagnostics`: desktop `App.svelte` watches the store; the phone takes its host's value at each connect, from `GET /settings/workbench`). No usage counters, no tracing.

- **Backend (Rust):** `src-tauri/src/observability.rs` exports `init(release)`, called once at the top of `lib.rs::run()` with the Tauri package version; the returned guard is held for the process lifetime (drop flushes). Captures Rust **panics** (incl. background threads) the frontend can't see. DSN inlined, overridable via `SENTRY_DSN` at build time. Release tag `workbench@<version>`.

- **Mobile:** same project, release `workbench-mobile@<version>`. Webview: `apps/mobile/src/sentry.ts` (`@workbench/telemetry`, prod-gated like desktop; also no fetch/xhr breadcrumbs, whose URLs carry addresses and tokens). Native: `sentry-android-core` in the `session-notifications` plugin (`Telemetry.kt`; auto-init off, started from the plugin's `load` in non-debuggable builds only), covering Kotlin crashes/ANRs plus the notification service's diagnostics — once-per-process warnings for a poll stall (>60s between polls outside Doze, with battery-optimization state; a Doze gap is only a breadcrumb), alerts blocked in Android settings, non-200 polls, unexpected exceptions; breadcrumbs for poll failures and alerts posted/skipped. Never record tokens, URLs or session titles. No Rust Sentry on mobile (thin shell).

- **Source maps:** release builds upload the frontend's hidden source maps through `@sentry/vite-plugin` (`scripts/sentry-vite.ts`, used by both apps' `vite.config.ts`), only when `CI` and `SENTRY_AUTH_TOKEN` (org secret) are both set (each desktop OS uploads its own bundle, Android only for tagged releases), under the same release name `Sentry.init` reports, then delete the `.map` files so they never ship. No token (local, PRs): no maps, nothing uploaded. A failed upload logs and the build carries on.

- **Prod/test gating (backend):** the Sentry client is a no-op when `cfg!(debug_assertions) || cfg!(test)` — so `cargo test`, `cargo test --release`, and `tauri dev` never report upstream.
