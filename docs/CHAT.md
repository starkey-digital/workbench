# Chat sessions

Claude and Codex chat sessions: the server side, the Workbench plugin link, the chat view, notifications and accounts. CLAUDE.md keeps a summary of each section.

## Transcript

`claude_transcript.rs` (+ `claude_transcript/`) — folds Claude session JSONL (history) and the stream-json lines the Workbench plugin translates a terminal `claude` into chat items: streamed text fills an item the final block replaces in place, tool results update their call, `can_use_tool` becomes an approval answered via `resolve_approval`, `control_cancel_request` expires an approval, and so does its call's tool result or the turn's `result` unless a background agent task still runs (an asking hook that died leaves no card answerable for nobody; `ModLink::keep_asks` drops those asks too). Claude MCP elicitations are answered only in the terminal: the plugin's `workbench_terminal_elicitation`/`_result` lines make a read-only `inTerminal` `Elicitation` item, cleared by its result or at turn end. `claude_transcript/elicitation.rs` (filters accepted content to the schema) serves Codex's `mcpServer/elicitation/request`. History follows the JSONL's `parentUuid` tree (`branch.rs`): a rewind leaves the old tail in the file as a dead branch, and `load`/`load_at(leaf)` show only the live one, as the CLI does. `protocol.rs` inventories, as handled or ignored, the SDK `SDKMessage` kinds (0.3.286 ↔ CLI 2.1.286) the plugin sends, the plugin's own, and the JSONL kinds; unknown kinds are logged once. `events.rs` folds side events into `Event` items (denied tools incl. `system:permission_denied`, hooks that failed/blocked/spoke from JSONL `hook_*` attachments + `stop_hook_summary` — never a line per successful hook — recalled memories, model refusals), `Artifact` results with a `url` into `meta.artifacts` (the link only exists in the structured result), and `prompt_suggestion` into `meta.promptSuggestion`, cleared when a turn starts. `goal.rs` folds `/goal`'s JSONL `goal_status` attachments into `meta.goal` (set: `met:false`+`sentinel`; a failed check: `met:false`+`reason`; achieved: `met:true`, plus a "Goal achieved" notice; cleared: `met:true`+`sentinel`); `/clear` ends it, `/resume` takes the resumed JSONL's. The plugin sees the attachment without its fields, so it sends `workbench_goal_status {uuid}` and the server folds the newest `goal_status` row in the JSONL tail once that one is written (`goal_status_entry`, retried briefly; `AgentSession::learn_goal_status`), and again at each `result` while a goal shows. Goal turns chain inside one turn (the goal's Stop hook blocks), so busy and the `result` need nothing special. Chat: `ChatGoal` above the composer (condition + the latest "not met yet" reason, live chats only).

## Plugin

`claude_plugin.rs` — embeds `plugins/workbench` (`register.ts` → `chat.ts`, every hook and `$` call → `link.ts` (server link, outbox, asks; every request bounded on `Date.now()` deadlines checked by the 50ms timer, each queued line and each settled request, asks and hellos also by a `$.clock.after`) + `lines.ts` (line builders) + `asks.ts` (pending `tool.check` asks, FIFO per tool+input), no engine calls; one hooks module per plugin, and `$` may only be spelled `$.noun.method(...)` inside a hook, never stored or passed) and writes it to `~/.workbench/claude-plugin/workbench`; `plugin_dirs_env()` is the `CLAUDE_CODE_PLUGIN_DIRS` every shell/chat process gets next to `WORKBENCH_HOOK_SOCKET`: our copy first, any other `*/claude-plugin/workbench` dropped. A Workbench started from another's terminal inherits that one's wiring, so desktop `run()` and the standalone `main` call `shell::scrub_inherited_env()` first thing (removes `shell::PARENT_ONLY_ENV` — `WORKBENCH_{MOD_URL,MOD_TOKEN,HOOK_SOCKET,PANE_ID,PERMISSION_MODE,MOD_PROCESS}` — and the inherited plugin copy), and server terminals, Codex chat processes and the `claude` probes `env_remove` those vars before setting their own. Replaced the old `workbench-hook-bridge` settings.json script for Claude (the desktop removes it at startup, `settings::remove_workbench_hook_integration`); Codex keeps its `notify` script. The plugin forwards `classic.*` hook events as an HTTP POST to the server's bridge (`apps/server/src/hook_bridge.rs` + `http.rs`, `application/json` only; the server stamps `WORKBENCH_HOOK_SOCKET` on every terminal and chat itself, so no client sends `hookSocket`, and mirrors a Codex TUI's finished turn into the attention feed), awaited for order but raced against a 3s `$.clock.sleep` (a hung bridge is then skipped 30s); `WORKBENCH_HOOK_SOCKET` is `host:port#secret`, a per-launch secret the bridge checks constant-time (`x-workbench-hook-secret` header; a `secret` field in Codex's notify-script lines; `HookBridgeState::address()` is the bare `host:port` for srt's allowlist). The repo is no longer a marketplace: `claude_plugin::disable_marketplace_install_at_startup` (desktop `run()` and the standalone server `main`, in a background thread; `spawn_disable_marketplace_install` also runs for accounts `save_workbench_settings` adds) reads each account's `plugins/known_marketplaces.json` read-only and, only when its `workbench` entry's source is exactly datstarkey/workbench or starkey-digital/workbench, runs `claude plugin uninstall workbench@workbench` and `claude plugin marketplace remove workbench` (`claude_accounts::claude_binary`, `CLAUDE_CONFIG_DIR` for non-default accounts). Workbench never edits those settings or registry files itself.

## Server

`agent.rs` + `agent/` + `agent_routes.rs` — chat-mode sessions for Claude **and Codex**. `AgentManager` owns the shared plumbing (id map + aliases, lifecycle lock, cap, summaries with `agent: "claude"|"codex"`, process groups, stop by pane or terminal for the workspace service's effects); `agent/driver.rs` is the per-CLI part (`Driver::{Claude, Codex}`: spawn args, stdout folding, client-message encoding — state machines, `session.rs` does the IO). Ids are global, so attach/message work by id for either kind. Sessions are started and ended only by the workspace service's effects (`workspace/exec.rs`: a Claude pane's terminal, a Codex `appServer` pane via `AgentManager::start`); the `/agent` routes list them and carry their IO. **Codex** (`agent/codex.rs`): one `codex app-server` per session (`WORKBENCH_CODEX_BIN` overrides the binary), `initialize` → `thread/start` or `thread/resume` (history paged from `thread/items/list`); a new thread's id is folded into its pane (`sessionAttached`); not blocked by `sandboxRuntimeEnabled` (srt never wraps Codex); modes are `CodexMode` presets applied as `turn/start` overrides; absent an explicit pick, `codex_config::chat_mode` resolves the server's saved Workbench launch preset for both desktop and mobile; prompts during a turn use `turn/steer`; meta carries `usageLimits` and `contextWindow` from the stream. `GET /agent` lists both kinds. **Claude**: there is no `claude -p`. A Claude chat is an **interactive `claude` in a server terminal**, made a chat by the Workbench plugin (`plugins/workbench/hooks/chat.ts`, see `claude_plugin.rs`): it translates the TUI session into the stream-json a `-p` session would print (`turn.step` chunks → `stream_event`s under one minted message id per model request, `session.append` rows → `user`/`assistant` lines stamped with that id and the request's `usage`, `tool.check` asks → `can_use_tool` via `/mod/ask`, `tool.call` results → `tool_use_result` (artifact links), Agent calls and forked skills (a Skill call whose agent has no `agent.spawn`) → `task_*`, `run_in_background` Bash → tasks ended by their own notification (`prompt.submit`, `origin.kind` `task-notification`, at idle or delivered into a running turn: each `<task-id>`/`<status>` in its text, so a killed job reports `stopped`; the Stop hook's job list is only the fallback, `hooks/jobs.ts`), `prompt.suggest` → `prompt_suggestion`, `session.measure` → `rate_limit_event` (with every window in `windows`, also sent at each hello from `$.session.usage()`) + `result.modelUsage`, the context window also as a model-less `system:init` `contextWindow` at session start, hello and whenever it changes (so a first turn shows it; never with `model`, which would drop the chat's `[1m]`; inits compare models ignoring `[1m]`), `/rename` (`command.run`) and the `session_title` of `SessionStart`/`UserPromptSubmit` → `custom-title` (a generated title reaches chat at the next prompt; no event carries it sooner; after an answered turn, for the first 3 prompts and every 5th after, `hooks/titles.ts` asks haiku for a better one, shown in chat at once and handed to the engine as the next prompt's `sessionTitle`; per-session state (opening prompt, a person's `/rename <name>`, which stops it) is kept in `$.store` so restarts carry on), a changed `$.command.list()` at each `turn.start` → `workbench_commands`, `classic.{PermissionDenied,PostModelSwitch,StopFailure}` → `system:permission_denied` / `system:init` / a failed `result`, refusals → `model_refusal_no_fallback`, `/clear` and `/resume` → `conversation_reset`) and turns stream-json input back into calls (`user` → `$.prompt.submit({asUser})`, which refuses a leading `/`, so a known `/command` → `$.command.run` (it skips the plugin's own `command.run` hook; `chatPrompt` emits the output, forked-skill tasks and a `result` itself; a panel command like `/cost` never resolves until dismissed in the TUI; since CLI 2.1.29x most local commands (`/goal`, `/goal clear`, `/rename`) resolve with no `text` and write their name and output as `session.append` `door: 'command'` rows, which the plugin forwards: the `<command-name>` row as a `user` echo (settles the chat's optimistic bubble; core shows it as `/x args`, not busy), the `<local-command-stdout|stderr>` row as `local_command_output`, with a matching `text` not shown twice; a command that resolves with `context` (notes for the model) gets 1s for its turn to start (`/goal`) before the plugin sends its `result`, so the chat doesn't flash idle and fire a completion), `interrupt` → `$.turn.abort` (with no turn running, a `result`, so Stop always ends the chat's wait; a chat prompt a hook refuses, or that fails in the plugin, gets an error `result` too, or a notice while a terminal-typed turn runs; a keep-alive that arrives mid-turn is dropped, and core ignores a queued keep-alive echo, since keep-alive mode would hide that turn's reply; the server marks a turn as a keep-alive (no "turn complete") only once its echo folds), `initialize` → the `/config` model list + `$.command.list()`, `set_model` → a session-only override applied to each main-thread `turn.step` (`next({ ...e, model })`, which takes an id: the server sends `resolvedModel` from `Transcript::resolve_model` over the pinned list, plus that model's `effortLevels`, forcing one fresh models probe when the pick doesn't resolve and refusing it if it still doesn't; the chat picker disables entries without a `resolvedModel` (the plugin's stand-in list) except the current one; the user's default model is never written). The override only replaces the model the engine names on its own (recorded at the first request after the pick), so a fallback for a step stands; an effort the picked model doesn't take is dropped (`system:init` `effort: null`). A person's pick in the TUI (`PostModelSwitch` `command`/`picker`/`sdk`) clears it. The server keeps each session's last `set_model` and effort (`AgentManager::set_model`/`set_effort`; the effort is forgotten on the plugin's `effortCleared`, a TUI pick) and re-sends it after a restart's hello (rewind, mode), unless a TUI pick (a `system:init` with another `modelChoice`) replaced it; optimistic in chat, a refused request rolls back its own pick with a notice, effort → a per-request override, cleared when the TUI changes effort; anything else, e.g. `set_permission_mode` (`$.config.set` would rewrite the settings default, not the live mode), is refused and the server restarts the terminal instead, see below. AskUserQuestion is asked from `tool.call` and a chat answer becomes the call's own `{ result }` (since CLI 2.1.292 a plugin's `allow` no longer dismisses the dialog of a tool that requires the person); ExitPlanMode stays the terminal's (its approval is what leaves plan mode, and only the dialog does that now): the plugin posts an `inTerminal` notice with Show terminal; the plugin registers `mcp__workbench__run_in_terminal` (`hooks/run.ts`, only under Workbench, not deferred) for a command the person must run themselves (logins, a TTY): its `tool.check` ask becomes `allow` (it runs nothing), and the call is held with `askInChat` as a `can_use_tool` the chat shows as `ChatRunCommand` (matched by its full name only, `isRunCommandTool`: another server's `run_in_terminal` runs commands and keeps its permission card; Run opens a new terminal tab via the host's `setRunCommand` context: desktop `runTaskInWorkspace`, phone `MobileClient.runCommand`; Done = allow, Skip = deny, each the call's text result; no chat could show it = a result asking for `! <command>`; the phone's home screen never answers it); `ChatMarkdown` also gives a Run button to `` `! <command>` `` code in Claude's own replies only (`runnable`, `bangCommand`), never tool output or subagent text; chat prompts a turn didn't read get a hidden `QUEUED_NUDGE`, not a resubmit). The server (`agent/modlink.rs`, `mod_routes.rs`) gives that exchange the same `Driver::Claude` + `Transcript` a pipe would: `POST /mod/hello` attaches (history loaded from the JSONL, the SDK `initialize` queued; answers `{inSeq, loaded}`: the newest `/mod/in` line acknowledged and whether history was loaded (only then does the plugin drop the `user`/`assistant`/`conversation_reset` and streamed (but `message_start`) lines queued meanwhile; task, notice and other lines history doesn't hold stay); a same-token hello (a lost reply, or the worker restarting, which sends a new `epoch` and numbers its lines from 1 again) re-sends the session's `set_model`/effort picks; each hello names its `claude` process (`process`: `WORKBENCH_MOD_PROCESS`, which the plugin sets in its own process, so a hot reload keeps it and a new `claude` in the same terminal doesn't), and one from a new process reloads the history and ends the old process's turn, asks and terminal dialogs (`AgentSession::restarted`); the first hello is bounded (5s) and a failed one is retried every 5s from the timer, never dropping the link), `POST /mod/out` feeds lines, `GET /mod/in` long-polls (20s, the plugin gives up at 30s) for input (with `ack=<n>` each line carries `wbSeq` and stays until a later poll acknowledges it, so a lost reply is redelivered; without `ack`, an older plugin, lines are drained), plugin lines (`/mod/out`, `/mod/ask`, `/mod/bye`) carry `seqs` (each line's number; `seq`, the first's, for an older server) and stay queued in the plugin until a reply confirms them, every request resending all unconfirmed lines from the oldest (over 5,000 queued during an outage, streamed deltas go first, then the oldest), and `ModLink::fold_new` folds each number once (absent `seq` folds all; a line whose fold panics counts as folded and is logged, so it can't block the lines after it); lines from a worker another has replaced get 409 and that worker says hello again (a replaced worker's hello is refused with 409 too, so two live ones can't take the link from each other), `POST /mod/ask` holds an approval until a client answers (`{answer}`, kept until the call's result so a retry after a lost reply gets it again; queued `lines` ride along so the asking hook never waits on the outbox, whose posts, like every plugin request, are given up after a bound because `$.http.fetch` can hang forever), or answers `{fallback}` when no chat has shown it (the TUI asks instead; once one has, it stays a chat's to answer while none is open, since a phone drops its socket in the background; a held request doesn't spend the plugin hook's time budget), `POST /mod/bye` (`{sessionId, lines}`: detaches the chat, the terminal keeps running); a link not polled for 45s is dropped (its `/mod/in` queue holds at most 256 lines / 16 MB meanwhile; more is refused with an error). Anything in the terminal holds its token (a prompt-injected Bash too), so a terminal opened for a session (`claudeSession`) is pinned (`ModGrant.session_ids`: that id, plus each a validated reset moved it to) and `/mod/hello` as any other id is refused; a plain shell or native terminal (empty list) runs whatever `claude` is typed, so it may attach as any id no live link holds. Only a stale link's session can be taken over by another terminal. `/mod/*` compares tokens in constant time. Auth is a per-terminal token (`WORKBENCH_MOD_TOKEN`, with `WORKBENCH_MOD_URL` = the first listener, the desktop's loopback one) built by `AgentManager::mod_env` for every server terminal (a macOS native pane is one too: `native_terminal.rs` is a SwiftTerm view over a server terminal, `TerminalManager::tap`, `TerminalMeta.native`), revoked when the terminal is gone; `/mod/*` finds a session by id or, after a `/clear`, by token. A Claude pane's spawn opens a server terminal running `claude --session-id|--resume <id>` (`claude_launch`, like every Claude terminal). `AgentManager::open_terminal` is the open-and-wait path for rewind, mode and account restarts. Claude Code's folder trust dialog comes before any plugin loads: the pane's runtime shows `needsTrust` (`claude_launch::shows_trust_prompt`) and the `trustFolder` command answers it (`TRUST_ACCEPT_KEYS`), so Claude Code records the trust itself. Stopping a chat kills its terminal (its `claude` is the chat's process); restarts are locked per session id. Chat attachments are saved by `agent/attachment.rs` (file names lose control characters, whitespace but spaces, quotes, backticks and `@`, so a name can't add or split a listed path) and named in the prompt line (`workbench_attachments`); the plugin appends those paths (never other `@words`) as "Attached files (read each with the Read tool): …" (plugin prompts never expand `@` mentions), which core strips from the bubble. `GET /agent` (`AgentSummary` per live session, built off the async workers like a WS snapshot since each takes the session's driver lock (a `/resume` reads its history outside that lock), newest change first: title, busy/`busySince`, the oldest unanswered approval as `waiting`, the running tool, `previousIds` from before a `/clear`), `POST /agent/claude/:id/message` (one WS client message over HTTP, e.g. answering an approval from the phone's home screen; 2 MB body cap, so image prompts stay on the WS), `GET /agent/files?projectPath=[&worktreePath=]` (the cwd's tracked + untracked, non-ignored files from `workbench_core::project_files`, capped; the cwd allowlist), `GET/POST /agent/plugins` (the chat `/plugin` sheet, `ChatPlugins` + `PluginManager`: core `claude_plugins` runs `claude plugin … --json` under the chat's account in its cwd; lists `user` plus that folder's `project`/`local` plugins, never `session`/`synced`, with up to 50 catalogue matches; a change is refused unless the id is installed in that scope (or, to install, in the catalogue), since `claude plugin enable` writes any id into settings; never passes `-y`, so a command-source install is sent to a terminal; changes apply on restart), `WS /agent/claude/:id/ws` (each also under `/agent/codex/…`) (`snapshot`, then `update` frames of `[index, item]` changes, coalesced per session to one frame per 50ms (`frames::FLUSH_EVERY`; other frames flush pending changes first, so order holds); a client attaching with `?meta=changed` (chat-ui's `agentWsUrl`) gets `meta` only when it changed, others on every frame; client sends `prompt`/`approve`/`elicit`/`interrupt`/`mode`/`restart` (Claude terminal sessions: relaunch under the same id and mode, a running turn included, via `AgentManager::restart_session`; not an End); many attachers, first approval answer wins; a Claude MCP elicitation counts as `waiting` with `tool: "Elicitation"`, `inTerminal`, until the plugin's answered line or the turn's end). The `claude` binary is resolved via `~/.local/bin` + the enriched PATH (GUI apps lack the shell PATH); its process group is ended when it exits (background shells included; on Windows `taskkill /T` while it's still alive). Start and stop share a lifecycle lock (held only to check, spawn or unregister: never across a process's exit or a history read), so concurrent starts of one id never spawn two processes (and the workspace model never shows two panes on one session); a stop unregisters under it, keeps the session in `exiting` by its ids, and shuts every stopped process down in parallel outside it, and a start (or plugin attach) of an id still exiting waits for it, so a new process never slips in while the old one exits; `Managers::kill_all` (pre-update) stops chat processes too. A finished session's WS is closed by the server. `/clear` re-keys the session to the new id (old ids stay aliases, `previousIds`; the cache policy moves); a `conversation_reset` whose id isn't a UUID or belongs to another live session is refused before the transcript resets (`AgentSession::apply_line` asks `feed_mod`'s alias, which validates and `session::rekey`s, never overwriting another session's id): the chat gets a notice and detaches from the terminal (whose `claude` now runs another conversation), so neither a forged line nor a `/resume` onto a session open elsewhere takes its id; `/resume` (`resumed: true`) loads that JSONL's history, drops the old ids and takes its own cache policy. **Rewind** (Claude only; Codex 0.160's `thread/revert` is conversation-only and unwired): the WS `rewind` message (`messageId`, `code`, `conversation`, `dryRun`, refused mid-turn). A plugin can't restore file checkpoints, so `code` dry-runs answer `{canRewind: false, error}` and real ones are refused (`agent_routes::rewind`); for `conversation` `AgentManager::rewind_terminal` kills the pane's terminal and opens a new one with `claude --resume <id> --resume-session-at=<the prompt's parentUuid>` (UUID only, unquoted: cmd.exe keeps quotes) under the same id; its history loads cut there, attached clients get `{"t":"replaced"}` and re-attach, and the desktop's hidden xterm follows the new `terminalId`. The new branch only lands in the JSONL with the next message. **Mode switch** (Claude terminal sessions): the WS `mode` message restarts the terminal the same way (`AgentManager::mode_terminal` → `restart_terminal`) as `claude --resume|--session-id <id> --permission-mode <mode>` (a picked mode is passed even when `default`, and kept across later restarts via `ModGrant.permission_mode`); refused mid-turn and for a native terminal's session ("Switch it in the terminal with Shift+Tab"). A restart holds the session's start lock, so two restarts never open two `claude`s; a client re-attaching on `replaced` retries while the new one attaches. **Prompt cache** (Claude only; `agent/cache.rs`, core `claude_transcript/cache.rs`): `TranscriptMeta.cacheExpiresAt`/`cacheTtlSecs` come from each call's `usage` (1h when it wrote `ephemeral_1h`, else 5m; reads keep the TTL and restart it; a compact clears it; the plugin's usage has no `cache_creation` split, so a terminal session keeps its known TTL and re-reads it from the tail of its session JSONL at each `result`, and at up to 8 `assistant` lines per session id until the file names one, so a first turn isn't stuck on 5m; CLI 2.1.300+ writes an `api-request` row with each call's `cacheControl` before the reply, so the first `assistant` line finds it). WS `cachePing` sends `KEEPALIVE_PROMPT` as a prompt, folded into one "Cache kept warm" notice (its reply never shows; the desktop ignores its `UserPromptSubmit` so the pane isn't flagged); `cachePolicy` (`keepWarmUntil` ≤24h ahead) is broadcast, saved per session id in `~/.workbench/chat-cache.json`, and run by one upkeep thread per `AgentManager` every 15s: within 2 min of expiry on an idle session it keeps warm (10 min for a 1h cache, ahead of the CLI's own idle compaction of 200K+ conversations at ~54 idle minutes, 2.1.299+), once per expiry. Compacting an idle conversation is left to the CLI's idle compaction. Chat UI: `ChatCache` chip + `ChatCacheHint` (cold cache on a large context offers Compact first).

## Chat view

`chat/` — Chat view of a Claude or Codex pane (`SessionChat` hosting `@workbench/chat-ui`; `chat-platform.ts` is the Tauri `ChatPlatform`; Terminal | Chat toggle in `TerminalGrid`). A Claude pane is one process: the chat is its terminal's `claude`, so its view is this device's choice only (`WorkspaceUi.chatPanes`). A Codex pane's view is its server-side mode (`setCodexMode`: the server stops one process and starts the other on the same thread). `AgentChat` only attaches: it opens `/agent/:kind/:id/ws` by id (the server follows `/clear`'s old ids; a session that isn't running is closed with code 4404); starting and ending are workspace commands. Approvals, interrupt and mode are native control messages. Send now (Ctrl/⌘+Enter while typing, or the chip on the newest message a running Claude turn hasn't read, `AgentChat.sendNow`) ends the turn, and the hidden `QUEUED_NUDGE` (`@workbench/types`; core and the plugin keep matching copies, checked by a core test) sent with `now` asks for the answer; background work keeps running. Which messages are unread is the server's: the plugin marks its mid-turn echo `workbench_queued` and sends `workbench_queued_read` when a model request reads it, and core folds both into `meta.unreadQueued` (cleared at turn end). Restart on an ended chat ("This session isn't running") calls the host's `onRestart` (the pane's `restart` command). A dropped socket or the server's `replaced` re-attaches with backoff from 1.5s doubling to 30s, giving up after 8 tries to `exited` + Restart (which re-attaches; a phone's wake retries); 4xx refusals stop at once; a 4404 is retried (about 45s) only after a `replaced` frame or while the host's `pane()` shows a newer spawn starting or running (the pane's `generation` past the one the last snapshot came from); otherwise the chat ends at once. **Drift and diagnostics** (`chat-diagnostics.ts` `ChatMonitor`): every chat keeps a 200-entry ring of socket and state events (counts and flags only: never text, ids, titles or URLs). A snapshot answering the chat's own `resync` is compared with what it showed (busy, item end, waiting, unread; mid-turn only busy counts) and a mismatch is reported as `chat.drift`; an unreadable frame as `chat.frame-error` and resyncs; an `update` whose index disagrees with the chat (`applyChanges` `aligned: false`) resyncs; busy with no frame for 60s resyncs (`stale`; not while it waits on the person; the wait doubles, up to 16 min, while a turn stays quiet); a resync the 5s throttle holds back for a misaligned update or bad frame is sent once it allows. Runs of updates fold into one trace entry. Reports go to `ChatPlatform.report` → `AgentChat`'s `report` option (`throttled`, once per type+agent per 10 min) → the host's `captureChatDiagnostic` (Sentry warning, trace attached as `chat-trace.json`); chat-ui never imports Sentry. Both hosts' chat menus have Resync now (`resyncNow`, past the 5s throttle; a re-attach on servers without resync) and Copy diagnostics (`AgentChat.diagnostics()` JSON). Transcript keys are unique: `earlierItems` drops ids the snapshot holds, `withHistory` joins Codex history pages with the live items. Assistant text renders as plain text, never `{@html}`. Attachments (paste, picker, Tauri drag-drop → `read_chat_attachment` / core `chat_attachment`; intake in chat-ui `attachment-intake.ts`): both agents accept images, PDFs (≤10 MB, base64) and UTF-8 text/code files of any extension (≤256 KB, text source) through one shared composer and intake. `agent/attachment.rs` saves uploads to a private per-session temp folder: Claude gets an "Attached files" list through its terminal plugin; Codex retains native image input and gets file references to read with its tools (PDF extraction depends on tools on the server). Both clean up uploads when their session ends (a pending bubble settles on an echo that has them appended). Typing `@` opens a file menu (`file-mentions.ts`; list from `GET /agent/files` via `AgentChat.listFiles`, cached 30s) that inserts `@path` (`@"…"` with spaces). `meta.retry` (Codex) / `rate_limit_event` drive the retry label and usage-limit banner; tool output over 4 KB is fetched on demand (`output`). Chats live in `chat-registry.ts` per pane; their approvals reach the pane's indicators and notifications from the server (`agent:attention`), not from the chat view. AskUserQuestion is a `can_use_tool` request answered with `answers` (question → label) merged into `updatedInput` (`ChatQuestion`); ExitPlanMode gets a plan card. Each prompt bubble has "Rewind to here" (hover, always shown on touch; Claude only, idle only): `AgentChat.beginRewind` dry-runs it in `ChatRewind` (code restore reports unavailable, see the server's Rewind), and a conversation rewind puts the prompt back in the composer via `onStarter`. MCP elicitations render as `ChatElicitation` (inline, or the phone's waiting sheet; Claude's are read-only `inTerminal`): form validation/coercion lives in `elicitation-form.ts`; URL mode opens only http(s) links (`url.ts` `safeExternalUrl`, the one shared guard) via `ChatPlatform.openLink`. Both hosts share `ChatDock` (composer stack) and `ChatAnswer` (approval/question/elicitation dispatch); `chat-registry` passes `AgentChat` a `ChatDraft` per pane so composer text survives a view toggle. Subagents and background jobs (`task_*` events → `meta.tasks`) show in `ChatTasks` (live output via `taskOutput`, found by `workbench_core::task_output` under `<temp>/claude[-uid]/…/tasks/<id>.output`), docked right on wide panes (`@5xl` container query) or as an overlay from the header. Artifact calls render as `ChatArtifactCard` (http(s) links only, opened via `ChatPlatform.openLink`); the header's Artifacts button opens `ChatArtifacts` (`chatArtifacts()` groups `meta.artifacts` by link; a `Sheet` on mobile). `ChatSuggestions` shows the prompt suggestion above the composer while idle with an empty draft. Every state is designed (starting skeleton, empty starters, optimistic prompt, thinking/writing/tool activity line, approval card, reconnecting bar, exited/failed with restart); animations respect `prefers-reduced-motion`. Mounted only while its grid is active.

## Notifications

**Notifications ("needs you") are event-driven:** Claude's plugin `/mod/out` and Codex's app-server stream update `AgentSession`, which publishes state transitions synchronously to `AgentManager.attention` (`attention_feed.rs`, one shared cursor-based history; no session polling). The desktop's `ServerControl::watch_attention` subscribes and emits `agent:attention`; Android's native background service consumes the exact same events through authenticated `GET /agent/attention?cursor=…` long polling, replays retained events after a disconnect, and clears resolved approvals. Token rotation/listener stop revokes outstanding requests. New subscriptions and server epochs seed silently; the latest 512 events are retained. Codex **terminal** `notify` payloads use `type: "agent-turn-complete"`; the hook bridge mirrors those completions into the same feed, while `codex:notify` only updates desktop labels/activity to avoid a second alert. A live Codex app-server session's notify is ignored because its stream already published the completion. Terminal notification links attach the existing server terminal and never start an app-server on the TUI's session file. `ClaudeSessionStore.onAttention` maps attention to the snapshot's pane by `paneId` (else the pane on that session) or notifies a session no pane shows by title; `resolved` withdraws it (`remove_native_notification`, macOS only). A terminal-owned dialog (`/mod/ask` fell back) stays `waiting` with `inTerminal: true` until resolved; keep-alive turns do not publish completions.

## Accounts

**Multiple Claude accounts** (`workbench_core::claude_accounts`, StatusBar `ClaudeAccountSwitcher`): each extra account is a `CLAUDE_CONFIG_DIR` (verified on Claude Code 2.1.286: it alone isolates the login, `.claude.json`, settings, hooks and `projects/`). Which account a launch runs under is decided only by the host, in `claude_accounts::for_launch` (at `newSession`): an explicit `claudeAccountId` (`''` = the default login), else for a Claude session the account whose dir already holds its transcript, else the project's own (`ProjectConfig.claudeAccountId`), else `activeClaudeAccount`, else the default login (a removed account is skipped). Clients send an id only for a known account (a resume); a new pane sends none and learns its account from the snapshot's pane `accountId`. The chat's usage chips follow `AgentChat.accountId` (`useAccountPlanUsage`), so a pick or switch never remounts the chat. Both switchers change the host's `activeClaudeAccount` through one core fn, `claude_accounts::set_active` (only that field is rewritten): the desktop's via the Tauri `set_active_claude_account`, the phone's via `PUT /settings/active-claude-account`; each bumps `Managers.settings` and `ServerControl::watch_settings` emits `settings:changed` so the desktop reloads. The resolved id becomes the shell's `CLAUDE_CONFIG_DIR` — clients send an id, never a path, and an unknown id is an error, never a fallback to the default login. Discovery scans every account dir and tags `accountId`; resume uses the owning account, restart keeps the pane's. **Account switch mid-chat** (Claude terminal chats, idle only; the Account entry of the composer's `ChatOptions` menu (mode, model, effort, account in one), and "Continue on …" on the usage-limit banner, desktop and mobile via `ChatDock`): the WS `account` message → `AgentManager::account_terminal` restarts the terminal like a mode switch, after `claude_accounts::move_session` **moves** (never copies: one id in two accounts resolves to either) the JSONL, its sidecar folder and `file-history` into the new account's dir; refused up front if that account already has the id. The snapshot carries `claudeAccountId`, and `AgentChat` follows it (`onAccount` → the phone's `ChatRef`); the workspace service folds a session's account into its pane's `accountId`, so a Restart from any device uses it. The old hook-script cleanup, the sandbox allowlist and session discovery all iterate `claude_accounts::config_dirs`; the Claude settings editor and plugin/skill listing still read `~/.claude` only. Login = `claude auth login` in a task tab under that account; who's logged in = `claude auth status --json`; plan usage = the latest `rate_limit_event` windows a live session of that account reported through the plugin (`UsageCache::note`, mapped by `claude_accounts::limits_from_windows` to the `/usage` labels: `five_hour` → `session`, `seven_day` → `week (all models)`; authoritative while a session of that account is linked, or for 60s after its last report, and never past a window's reset; `fresh=true` with no linked session goes to the probe), else `claude -p /usage --no-session-persistence`; served as `GET /agent/usage?claudeAccountId=[&fresh=true]` (`apps/server/src/usage.rs`: the probe cached per account 60s, `fresh` accepts ≤10s, concurrent requests share one run; beside a reading the probe still runs every 15 min, behind, for the per-model weekly limits only `/usage` prints) to both the chat chips (`usePlanUsage`, one shared poller per server+account) and the switcher; the CLI prints plain text (`parse_usage` reads `Current <label>: N% used · resets …` lines, empty when logged out or if the wording changes; the flag stops each check writing a transcript). Model list = `claude_accounts::models`: a `claude -p` in the session's cwd sent only the `initialize` handshake (no model call, hooks off via `--settings`), cached 1h per account+cwd and kept in `~/.workbench/models-cache.json` (`usage.rs` `AccountCache`; past 1h the old list is served and refreshed behind and the newer one re-pinned onto every session of that account+cwd; only a missing entry waits; entries saved over 7 days ago or for a cwd that's gone are dropped; a failed run is kept 30s, never saved, and never replaces the last good list; saves are written off the async thread); the mod's `/mod/hello` pins it onto terminal sessions (`Transcript::pin_models`) over the plugin's guessed `/config` list. The plugin also names the `/config` pick (`modelChoice` in its `initialize` reply) and sends a `system:init` with the resolved `model`/`effort` whenever they change.
